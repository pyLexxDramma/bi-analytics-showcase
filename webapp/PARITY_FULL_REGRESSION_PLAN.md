# План: полный регресс паритета main ↔ showcase

Отдельный план повторного прохода **всех** экранов (включая уже принятые в `PARITY_ACCEPTANCE.md`).  
Журнал детальных заметок по экранам по-прежнему ведётся в [`PARITY_ACCEPTANCE.md`](./PARITY_ACCEPTANCE.md).  
Этот файл — **чеклист прохода и правила цикла**.

| | |
|---|---|
| Репозиторий правок | `bi-analytics-showcase` (`webapp/`) |
| Эталон UI/цифр | `[main]` Streamlit (`bi-analytics` / `:8501`) |
| Стенд showcase | CloudPub / VPS webapp (Next + FastAPI) |
| Старт цикла | 02.08.2026 |
| Текущий экран | ✅ §1 → 🔄 §2 БДДС (расходы) |
| Mobile | обязателен на **каждом** экране (тот же URL, ~390px) |

**Правила цикла (зафиксировано):**

- Репозиторий правок — только `bi-analytics-showcase`.
- Main Streamlit = эталон цифр и структуры.
- Перед сверкой — одна `version_id` (gate §3).
- ✅ в матрице — только после приёмки **на стенде** (не локально).
- Mobile сразу на каждом экране, тот же адрес (responsive + drawer).

---

## 1. Цель

Привести showcase в **полное соответствие** с оригиналом (main) по:

- составу блоков, вкладок, кнопок (Скачать, зум);
- фильтрам / чекбоксам / radio (набор, дефолты, поведение вкл/выкл);
- корректности цифр и таблиц (**main = идеал**);
- **mobile layout** на том же URL (~390px): drawer-меню, читаемые фильтры/таблицы/KPI (цифры как main; UI удобнее Streamlit);
- где уместно — улучшить отображение через Tremor **без** расхождения с main по данным и структуре.

Параллельно оптимизировать showcase (скорость, кэш, путь данных через `core_bridge` / ту же логику, что main), не обгоняя текущий экран по матрице.

## 3. Gate: одна версия данных (перед каждым экраном)

Без совпадения версий цифры не сравнивать.

1. Main: сайдбар «Версия данных» — зафиксировать активный снимок (`id`, `created_at`, файлов, строк).
2. Showcase: тот же снимок активен (список версий в сайдбаре / `GET /api/versions`).
3. В заметку экрана записать: `version_id=N · YYYY-MM-DD HH:MM · files/rows`.
4. При расхождении: FTP + перезагрузить БД / activate — затем снова gate.

Дополнительно перед §1: приёмка сайдбара FTP + список версий на стенде (если ещё не ОК после `d3c7777`).

```text
main active version ──┐
                      ├── одинаковые id/дата/files/rows ──► скрины + smoke
showcase active ──────┘
```

## 4. Цикл на один экран (строго)

| Шаг | Кто | Действие |
|-----|-----|----------|
| 1 | Пользователь | Desktop: скрин main (дефолты) + скрин showcase (те же фильтры, та же version_id) |
| 2 | Пользователь | Mobile showcase ~390×844: дефолты + 1 ключевой фильтр вкл/выкл (тот же URL) |
| 3 | Пользователь | 1–2 ключевых фильтра/чекбокса desktop вкл/выкл — пары скринов |
| 4 | Агент | Анализ расхождений (UI + цифры + mobile layout + логика API) |
| 5 | Агент | Правки showcase; при необходимости Tremor-улучшения |
| 6 | Агент | Локально: smoke / проверки; пользователь «ок» (desktop + mobile) |
| 7 | Агент | Commit/push **только по просьбе** после локального «ок» |
| 8 | Пользователь | Приёмка на **стенде** после деплоя (desktop + ~390px) |
| 9 | Агент | Только после стендового «ок»: ✅ в этом плане + запись в `PARITY_ACCEPTANCE.md` |
| 10 | — | Следующий экран. Баги со стенда — в текущем §, без прыжка вперёд |

Правило деплоя: локальное «страница 200» ≠ приёмка. См. `deploy-acceptance-first`.

### Mobile (обязательно, не «потом»)

Тот же URL; не отдельный `m.`-сайт. Цифры = main; layout на узком экране — лучше Streamlit.

| Ширина | Ожидание |
|--------|----------|
| &lt; lg (1024px) | hamburger → drawer-сайдбар; фильтры стеком; таблицы `overflow-x-auto`; KPI 1→2 кол. |
| lg+ | текущий desktop (сайдбар слева sticky) |

На каждом экране: меню/drawer, touch ≥44px, графики ~220–280px высота, ИТОГО не обрезать. Баги chrome (меню/фильтры) — в shared, не копировать на экран.

## 7. Параллельная оптимизация (не срывает порядок)

Делать на фоне текущего § или между экранами:

- API тонкий слой + disk-кэш / jobs (анти-502).
- Сервисы 1:1 с main (`finance_1c`, `core_bridge`), без упрощённых обходов.
- Расширение `scripts/parity_smoke.py` для экранов без smoke.
- Скорость ответов **при тех же цифрах**, что main на той же версии.

Критерий: быстрее и точнее относительно main, не «быстрее ценой других цифр».
