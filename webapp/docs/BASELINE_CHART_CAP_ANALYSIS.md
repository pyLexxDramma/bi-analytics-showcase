## 3. Поведение: таблица vs график vs «Детализация»

> **Обновление (заявка #16 / report #21):** основной график больше не `rd_end_bars`.
> И график, и таблица строятся из **одного level-scoped среза MSP**; порядок строк —
> как в исходном CSV (`_msp_ord`), не по `plan_end_diff`. `chart.kind = end_bars`
> (ковенанты по-прежнему `covenant_points`). `CHART_CAP=400` режет первые 400 в
> MSP-порядке. Функция `_build_rd_deadline_chart_df` оставлена, но не используется
> основным путём.

```text
MSP → фильтры проекта/блока/строения
        └─→ фильтр Детализация ур.4|5 → scoped
              ├─→ table (dates: neg end / reasons: maket) — sort _msp_ord
              └─→ chart.rows end_bars — sort _msp_ord → head(CHART_CAP=400)
```

| | Таблица | График / Gantt | Ур.4 / ур.5 |

| **Baseline** | без лимита | cap 400 | на таблицу и график — **одинаково** (после #16) |

### Семантика графика baseline (после #16)

Дефолтный график — **level-scoped задачи MSP** (`chart.kind = end_bars`):

- тот же срез, что таблица после фильтра детализации (при `show_reasons` — forcе ур.5);
- сортировка по порядку строк исходного MSP;
- затем `head(400)`.

Ковенанты → `covenant_points` (точки, не полосы).

Исторические замеры ниже (§4) сняты до смены семантики (`rd_end_bars`) — для сравнения cap/payload, не как актуальный `chart.kind`.

**Вывод по Excel «детализация одинаково на оба»:** для baseline после #16 — **да** (кроме режима ковенантов).

## 5. Подгрузка «частями» — помогает ли?

| Подход | Payload / API | Рендер браузера | Вердикт |
|--------|---------------|-----------------|---------|
| Чанки API → потом один Plotly на всё | лучше старт | почти не лучше | слабо |
| Windowed / virtual: только видимое окно (+ буфер) | лучше | **сильно лучше** | да, если нужен полный гант |
| Пагинация «по 50» без полного ганта | лучше | лучше | это уже не «все сразу» |
| Агрегация на графике + детали в таблице | уже ок | уже ок | совпадает с main (baseline) |

**Итог:** частичная подгрузка помогает **только вместе** со сменой рендера (не держать все полосы в одной фигуре). Сама по себе пагинация API — слабый рычаг. Сложность windowed Plotly — порядка **L**, не мелкий патч.

### 6.1 Вариант E\*: «все задачи на диаграмме», но без подвисаний

**Смысл для клиента:** как «убрать лимит и показать все».  
**Технически нельзя:** просто снять `CHART_CAP` / `GANTT_CAP` и оставить текущий Plotly на полную высоту `n` — это как раз путь к подвисаниям (на снимке уже 968–5565 строк в таблице schedule).

Подвисание даёт не «много данных в принципе», а то, что **браузер сразу рисует все полосы** (десятки–сотни тысяч px SVG). Нужно: данные полные (или по окнам), **в DOM — только видимое**.

**Что делать, чтобы избежать подвисаний**

1. **Виртуальный / windowed гант (главный путь)**  
   На экране ~30–80 полос + буфер; при скролле пересобирать только окно. Для пользователя — «листаю все задачи»; для браузера — постоянно мало узлов.

2. **Не полный Plotly на 1k+ строк**  
   Для полного режима — HTML/CSS или canvas + virtual list; Plotly оставить для малых срезов / обзора РД. Текущая связка «Plotly + height = n×44–48px» — узкое место.

3. **API отдаёт окно (offset/limit), не весь гант сразу**  
   Таблицу можно полной или тоже страницами. Снижает JSON (на «Все» detail уже ~2.2 MB при cap).

4. **Правила на «Все проекты»**  
   Даже с виртуализацией 5k+ тяжело: полный гант — при **одном проекте**; на «Все» — сводка / топ / «выберите проект».

5. **Облегчение полного режима**  
   Без дат на каждой полосе; debounce скролла; не пересобирать layout на каждый пиксель.

**Что почти не спасает**

- поднять/снять cap, оставив текущий Plotly;
- грузить JSON чанками и склеить один огромный график.

**Формулировка**

> E\* = желание клиента («все на диаграмме») + виртуальный рендер. Это отдельная фича уровня L (не тюнинг константы), с апрувом. Старт логичен с **«График проекта» + один проект**, где cap уже болит. На baseline дополнительно нужна смена/режим «как в таблице», иначе «все задачи» всё равно не совпадёт с текущим РД-графиком.

**Объём (ориентир):** windowed/virtual gantt — L; смена бэкенда на окна — M; плюс на baseline режим «как таблица» — M–L. Апрув владельца обязателен.

## 8. Рекомендация

### Основная (клиенту / владельцу)

**Не снимать cap и не обещать «все 1500+ на графике».**

1. **Baseline «Отклонение от базового плана»:** график = дедлайны разделов РД (как main); полный список — таблица + «Детализация» ур.4/5. Замечание Excel для baseline — либо отклонить со ссылкой на main, либо вынести в режим «Как в таблице» (#5), не менять дефолт молча.
2. **Project schedule:** уровень уже влияет одинаково; при 1500 задачах cap 600 ожидаем. Ответ: один проект + ур.4 для обзора / ур.5 для деталей в таблице.
3. **Запасной:** адаптивный cap (#3) с опорой на §4: multi оставить 400/600; single на schedule можно обсуждать ~800–1000 (у Есипово detail table=1417), но только с апрувом и повторным замером UI. Не в ноль.
4. **Если жёстко «все на диаграмме»:** это вариант **E\*** (§6.1) — виртуальный гант / windowed, возможно без Plotly на полном списке; плюс на baseline режим «как в таблице». Не raw uncapped Plotly (#17). Запасные полегче: топ-N (#4) или export (#10).
