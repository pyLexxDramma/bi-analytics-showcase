# Что дашборд должен передавать в XCA: контракт ссылки под роли

Замер на стенде `insipidly-carefree-husky.cloudpub.ru` 12.08.2026 под тестовым
пользователем `demo_colleague` (роль «Демо: девпроекты / сроки / предписания»,
проекты «Дмитровский», «Есипово-5», экраны `developer-projects`,
`project-schedule`, `prescriptions`).

Документ отвечает на один вопрос: **какие параметры нужны XCA, чтобы
разграничение ролей работало на нашей стороне.** Причина, по которой этого не
хватает сегодня, — у XCA нет доступа к `roles-catalog` (токен не выдан), и
единственный источник прав для него — сама ссылка.

---

## 1. Что передаётся сейчас (факт)

### Кнопка «Спросить ИИ» (в шапке экрана)

Дашборд делает `POST /api/ask-ai/link` и открывает подписанный URL. В ссылку
уходит:

| Параметр | Пример | Комментарий |
|---|---|---|
| `v` | `1` | версия контракта |
| `report` | `screen_developer_projects` | экран в номенклатуре XCA |
| `q` | `Объясни дашборд «Девелоперские проекты»` | вопрос по умолчанию |
| `ctx` | `Отчёт «Девелоперские проекты». Матрица…` | описание экрана |
| `project` | `Дмитровский` | **один** проект |
| `uid` | `u_2` | идентификатор пользователя |
| `role` | `demo_colleague` | код роли |
| `src` | `developer-projects` | откуда пришли |
| `ts`, `sig` | | время выпуска и подпись HMAC |

### Кнопка «ИИ помощник» (в меню слева)

Обычная ссылка `target="_blank"` прямо на корень XCA. **Ни одного параметра,
ни подписи** — то есть XCA не знает ни пользователя, ни роли и открывает общий
чат с полным доступом. Это главный пробой: любой пользователь любой роли
получает через неё неограниченного ассистента.

---

## 2. Чего не хватает и почему

### 2.1. `projects` — весь набор проектов пользователя, а не один

Сейчас уходит `project=Дмитровский`, хотя у роли их два. Проверено: на экране
«Девелоперские проекты» с фильтром «Дмитровский|Есипово-5» в ссылку ушёл только
первый.

Почему это блокирует разграничение: XCA режет **данные** по набору проектов
(витрина строится по хешу отсортированного набора). Один проект из двух — это
не «права», а «текущий фильтр экрана»: по нему нельзя решить, что пользователю
можно, а что нет. Ответ на вопрос «а по второму объекту?» либо будет отказан
неправомерно, либо, наоборот, посчитан по всему портфелю.

**Нужно:** `projects=Дмитровский|Есипово-5` (полный `allowed_projects` из
`/api/auth/me`), значение `*` — если доступны все.
`project` оставить как есть — это подсказка «на что человек смотрел».

### 2.2. `reports` — список доступных экранов

Сейчас передаётся только `role`. Состав прав роли XCA взять неоткуда: к
`roles-catalog` нужен `ADMIN_SYNC_TOKEN`, которого нам не выдали. Пока его нет,
единственный рабочий вариант — прислать права в ссылке.

**Нужно:** `reports=screen_developer_projects,screen_project_schedule,screen_prescriptions`
(в номенклатуре `screen_*`, не `nav.id`), `*` — если доступны все.

Даже когда токен появится, параметр стоит оставить: он позволяет XCA ответить
правильно, если каталог временно недоступен, а подпись не даёт его подделать.

### 2.3. `period` и `filters` — то, что человек видит на экране

В теле `POST /api/ask-ai/link` эти поля предусмотрены, но фактически не
передаются ни на одном из проверенных экранов. Без них ассистент считает за
весь срок, и его цифры не сходятся с экраном, с которого пришёл пользователь, —
а заказчик сверяет именно это.

**Нужно:** `period=2026-08` (или `date_from`/`date_to`) и `filters={"…":"…"}`
в JSON, как уже описано в контракте v2.

### 2.4. `exp` — явный срок годности

Сейчас срок считается от `ts` по нашему TTL (10 минут). Лучше передавать
`exp` явно: тогда срок задаёт тот, кто выпускает ссылку, и его видно в аудите.

---

## 3. Кнопка «ИИ помощник» — тот же вход, что и «Спросить ИИ»

Она обязана идти через `/ask` с подписью. Отличие только в том, что экрана нет:

* `screen=free` — XCA это уже поддерживает (открывает чат без привязки к отчёту);
* `q` — пустой (вопрос напишет пользователь), `ctx` не нужен;
* `uid`, `role`, `projects`, `reports`, `ts`, `sig` — **обязательны**, как и у
  контекстной кнопки.

Пока она ведёт на корень XCA напрямую, любые ограничения роли не действуют:
пользователь попадает в общий чат, где данные не срезаны.

---

## 4. Формат значений

| Параметр | Формат | `*` означает |
|---|---|---|
| `projects` | имена через `\|`, точно как в дашборде | все проекты |
| `reports` | `screen_*` через запятую | все экраны |
| `uid` | стабильный идентификатор пользователя | — |
| `role` | код роли латиницей (`demo_colleague`) | — |
| `period` | `YYYY-MM` либо `date_from`/`date_to` в `YYYY-MM-DD` | — |
| `filters` | JSON-объект «поле → значение» | — |

Все параметры входят в строку подписи (иначе их можно подменить в адресной
строке — а именно они теперь определяют доступ).

---

## 5. Ловушка: имена проектов расходятся

Дашборд для этой роли отдаёт **«Дмитровский»**, а в данных, по которым считает
XCA, проект называется **«Дмитровский-1»** (есть ещё вариант написания
«Дмитровский1»). Сверка имён у нас строгая, без мягкого сопоставления, и это
осознанно: «Есипово» и «Есипово-5» — разные объекты, и нестрогое сравнение
открыло бы доступ к чужим данным.

Следствие: если прислать `projects=Дмитровский`, XCA не найдёт такого объекта и
роль получит пустой ответ или отказ.

**Нужно одно из двух** (решение за командой дашборда):

1. присылать имена ровно так, как они приходят в выгрузках 1С/MSP
   («Дмитровский-1»), либо
2. присылать идентификаторы проектов (`ID_Проекта` из 1С) — тогда написание
   вообще перестаёт иметь значение, и это предпочтительнее.

---

## 6. Как проверить, что всё сошлось

1. Открыть ассистента кнопкой под ролью с ограничением по проектам.
2. Спросить портфельный отчёт («покажи план и факт по бюджету по всем
   проектам») — ожидается отказ, а не цифры.
3. Спросить разрешённый отчёт — ожидается таблица **только** по своим объектам,
   без упоминания чужих.
4. Проверить второй объект роли: он должен отвечать так же, как первый (это и
   ловит недостающий `projects`).
